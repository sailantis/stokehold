## Fork: yes, you get a consistent point

Forking from a PHP process does give every child the same starting state — the child is a byte-identical COW copy of the parent's heap at the fork point. Deterministic, repeatable.

Caveats: fork from a **clean, idle, post-boot** state. Not mid-query, not with buffered output pending, not holding a DB transaction. And children diverge after their first write, so treat the shared baseline as read-only.

## But you're right that a forked child can't do CGI

A forked child is a **plain PHP process**. It has no SAPI able to populate `$_SERVER`, `$_GET`, `$_POST`, `$_FILES`. And this is precisely what FFI cannot fix:

| CGI needs | Where it lives | FFI reach? |
|---|---|---|
| Multipart/`rfc1867` body parsing | `sapi_module.read_post` C callback | No |
| `$_FILES` + upload temp files | SAPI globals (`SG()`) | No |
| `is_uploaded_file()` / `move_uploaded_file()` | C-level origin check | No |
| `php://input`, `CONTENT_LENGTH` handling | SAPI request info | No |

These aren't functions you can call — they're **C callbacks PHP invokes during request startup**. Userland can't register them; assigning `$_POST` by hand is not the same thing (and can't replicate upload validation). This is the same capability floor as before: FFI can call leaf functions, not install SAPI hooks.

So your instinct is exactly correct: *something is missing.* The missing piece is **the SAPI itself** — and that's C, by design.

## The resolution

Don't build the FastCGI worker. **`php-cgi` already is one.**

Verified behavior: `php-cgi -b` runs a full FastCGI event loop, handling many requests per process sequentially. Per request it re-initializes superglobals, re-parses POST bodies and multipart/`$_FILES`, and runs `request shutdown` resetting globals. That's **full FPM-grade reset, for free, in C, outside userland** — exactly the thing you've been trying to reach with FFI and embedding.

And it's already on your machine. From your PHP install:

```
C:\php-8.3.31\php.exe           ← CLI, for persistent workers
C:\php-8.3.31\php8embed.lib     ← embed SAPI (not needed)
```

Windows **has no `php-fpm` at all** — which is why IIS has always driven `php-cgi` through FastCGI. That's the gap your server fills, and it's a real one.

## The architecture that gets both your goals

One Rust supervisor, two pool types, same routing/routing code:

| Pool | Worker | Reset mechanism | Linux | macOS | Windows |
|---|---|---|---|---|---|
| **Worker** | your persistent entry point | `clearRequestScope()` + recycle | ✓ | ✓ | ✓ |
| **FPM-like** | `php-fpm` (Linux) / `php-cgi -b` | **full SAPI per request** | ✓ | ✓ | ✓ `php-cgi.exe` |

Your server's job in the FPM-like pool is exactly what `php-cgi` lacks: **spawning, supervising, health-checking, recycling, and routing**. You never touch PHP internals — you manage processes and speak FastCGI, which is a documented protocol on a socket.

So:

```
nginx ──FastCGI──► ┌─ pool: persistent workers   (your protocol)
                    ├─ pool: php-cgi / php-fpm    (their SAPI does the reset)
                    └─ HTTP + rustls + ACME       (nginx replacement, auto-certs)
```

## What this buys you

- **Both modes**, not one. Worker mode where persistence wins; full-reset mode where correctness wins.
- **Real reset semantics** — `$_POST`, `$_FILES`, multipart, `is_uploaded_file()`, all of it — because PHP is doing it in C.
- **Zero FFI, zero embedding.** No ABI, no per-version rebuilds, no isolation loss.
- **All three platforms**, including the Windows case that has no native answer today.
- **nginx replacement + auto-certs** are orthogonal and identical in every design — `hyper` + `rustls` + `rustls-acme`.

And on Linux you can still add prefork later to cut the *worker* pool's bootstrap cost. It's simply irrelevant to the php-cgi pool, which re-boots per request by definition.

## It's not a forward proxy

A forward proxy speaks the **client's** protocol and relays it. You'd be **terminating** HTTP and **originating** FastCGI — a protocol gateway, i.e. an app server. The practical consequence: you're not relaying bytes, you're *translating* between two protocols, and you own both ends.

## The pipeline

```
nginx / client
     │  FastCGI (or HTTP)
     ▼
┌─────────────────────────────┐
│  Rust master                │
│  ├ listener (FastCGI/HTTP)  │   ← terminates client protocol
│  ├ dispatcher: pick a slot  │
│  └ FastCGI client task ─────┼──► 127.0.0.1:19001  php-cgi.exe
└─────────────────────────────┘   127.0.0.1:19002  php-cgi.exe
                                  127.0.0.1:19003  php-cgi.exe
                                  127.0.0.1:19004  php-cgi.exe
```

The inner arrow is the part people miss: your dispatcher becomes a **FastCGI client**. It sends `BEGIN_REQUEST` → `PARAMS` → `STDIN` to a php-cgi backend and reads back `STDOUT` → `END_REQUEST`. Then it re-frames that response as FastCGI back to nginx.

## On Windows: yes, one process per port

You need **N processes on N distinct ports**. There's no way around it:

- `PHP_FCGI_CHILDREN` works by `fork()` — **impossible on Windows**. So php-cgi can't spawn its own children there.
- Multiple processes binding the *same* port via `SO_REUSEADDR` doesn't load-balance on Windows — it's not a pre-fork socket.
- FastCGI has request IDs, so you *could* multiplex over one connection — **don't**. php-cgi processes sequentially, so multiplexing buys nothing and adds a demux table you don't need.

So model each backend as a **slot**, exactly as you described. On Linux you get more options (real `php-fpm` with a pre-forked pool, or `PHP_FCGI_CHILDREN`) — but the Windows shape works there too, so it can be one code path.

## What php-cgi does for you vs. what you write

| You write | php-cgi does |
|---|---|
| Spawn/supervise N processes | Bind and accept |
| Assign a port per worker | Parse CGI params from FastCGI records |
| Health check, restart on crash | **Parse multipart / `$_FILES` from the raw body** |
| Translate HTTP → FastCGI PARAMS | Populate `$_SERVER`, `$_GET`, `$_POST`, `$_COOKIE` |
| Frame requests, pipe response bytes | `request_startup` + `request_shutdown` |
| Pick a free slot | Upload temp files, `is_uploaded_file()` |

That middle column is the whole point. **You never parse multipart.** You pass `CONTENT_TYPE`, `CONTENT_LENGTH`, and the raw body as `STDIN`; php-cgi does the `rfc1867` parsing in C. That's the work FFI couldn't have done for you, and it's already written.

## Three operational details that will bite you

**1. Drain `STDERR` per backend, always.** php-cgi writes errors to `STDERR`. FastCGI has a dedicated `STDERR` record type. If your client doesn't read it, the pipe buffer fills and the backend blocks forever. One reader task per backend, non-negotiable — this is the classic "why did all my workers hang" bug.

**2. Connection reuse is not guaranteed.** FastCGI keep-alive depends on the `FCGI_KEEP_CONN` flag *and* the server honoring it. FPM supports it; php-cgi's behavior you should measure. If it closes after each request, you pay a TCP connect per request — cheap on loopback, but model it as a slot-level connection state machine rather than assuming persistence.

**3. Windows process hygiene.** No unix sockets — loopback TCP only. And if your master dies, its `php-cgi` children survive as orphans. Use a **Job Object** with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` so the OS reaps them; on Linux the equivalent is `PR_SET_PDEATHSIG` or a process group. Do this early — orphaned php-cgi processes holding ports will make your dev loop miserable.

## The routing rule

One dispatcher serves both pool types, and the choice is per-vhost or per-route:

- **Worker pool** → your persistent entry point (boots once, `clearRequestScope()`, recycled by RSS).
- **FastCGI pool** → `php-cgi`/`php-fpm`, full per-request reset, arbitrary `SCRIPT_FILENAME`.

Requests that need real isolation or use SAPI-specific APIs go to the second; hot paths verified worker-safe go to the first. Same listener, same PARAMS parsing, different backend.

That's the Windows pipeline, and it's a genuine capability — there is no native equivalent on Windows today, which is why IIS drives `php-cgi` by hand.

Make a FastCGI backend an enum with three modes, so one dispatcher serves everything:

```yaml
fastcgi_pool:

  socket: unix:/run/php/php8.3-fpm.sock
```

## Don't reimplement what php-fpm already does on Linux

- process pool management (`pm.max_children`, `pm.start_servers`, `pm.max_spare_servers`)
- **`pm.max_requests`** — the recycling you were planning to build
- **multiple pools in one master** — different users/sockets per vhost, which is how you get multi-tenancy
- slow log, status page, graceful reload (`SIGUSR2`)
- proper logging and `chdir`/`chroot` per pool

Building any of that in Rust on Linux would be strictly worse than using it.
